# Standard Operating Procedure (SOP) для инструментов агента

Документ описывает для каждого инструмента (`src/tools/*.tool.ts`), вызываемого
агентом через `BillsCycleService` (`src/services/BillsCycleService.ts`) и типизированный
диспетчер `callTool` (`src/tools/registry.ts`):

- **когда** агент вызывает инструмент;
- **как** формируются аргументы вызова;
- **как** обрабатывается результат;
- **как** обрабатываются ошибки;
- **какие ограничения** соблюдаются.

## Общие правила для всех инструментов

### Когда использовать инструмент
- Инструмент вызывается только внутри соответствующего режима (`bills`/`continue`/`continue!`),
  никогда — по свободной инициативе модели в других режимах (`ask`, `askMeters`, `meters`, `report`
  инструменты не вызывают вовсе, см. `Readme.md`, раздел "Роутинг моделей").
- Перед вызовом любого инструмента, привязанного к обработке счетов, агент обязан пройти через
  единый роутер `agentModelRouter` (`resolveModeWithLog` / `validateBillCategories` и т.п.),
  который определяет режим EASY/HARD для конкретной задачи по описанию команды через локальный
  классификатор. Инструмент сам не выбирает модель — выбор происходит до вызова инструмента
  (см. `ReceiptVerificationService`, `SordisuBillGeneratorService`). Документные операции роутера
  при недоступности RouterAI (сеть/5xx/таймаут) выполняют fallback на локальную Ollama по
  извлечённому из документа тексту.
- Инструменты вызываются только **прямым вызовом агента** (`runBillsReactCycle`,
  `checkBillReceipts`, `generateSordisuBill` в `BillsCycleService`) — агент детерминированно
  вызывает `callTool('<имя>', args)` с аргументами, построенными из уже известных данных
  (например, из результата валидации), а не через парсинг ответа LLM, чтобы исключить
  потери/искажения данных при парсинге текста модели. Свободный tool-calling чат
  (`processMessage`/`chatWithTools`) из проекта удалён как неиспользуемый.

### Как обрабатывается результат
- Вызов инструмента — прямой вызов функции внутри процесса; результат — типизированный объект
  (интерфейс результата объявлен рядом с инструментом: `OrganizeBillsResult`,
  `ReceiptsCheckResult`, `GenerateSordisuBillResult` и т.д.).
- Тип результата выводится из имени инструмента (перегрузки `callTool`), кастов
  вида `as unknown as X` нет.

### Как обрабатываются ошибки
- Ошибка внутри инструмента — это обычное исключение (`throw`), которое распространяется
  к вызывающему коду и перехватывается в соответствии с логикой шага цикла.
- Для шагов ReAct-цикла, которые не критичны для основного результата (организация файлов,
  дозапись таблицы учёта, актуализация векторной базы, удаление служебных манифестов), ошибка
  логируется (`console.error`), но **не прерывает** выполнение цикла — валидация уже прошла,
  поэтому агент продолжает и возвращает уже накопленный результат as-is.
- Ошибки скачивания с Яндекс.Диска и валидации категорий (шаги 1-3 `runBillsReactCycle`) —
  критичны: при них цикл сразу завершается с `valid: false` и собранным списком `errors`, без
  попытки продолжить дальше.
- Ошибки `check_bill_receipts` и `generate_sordisu_bill` прерывают выполнение вызывающего кода
  (в отличие от "мягких" шагов ReAct-цикла), приостанавливая цикл `continue` и требуя
  вмешательства пользователя (Human-in-the-Loop).
- Отдельно обрабатывается исчерпание токенов/баланса RouterAI: ошибка помечается флагом
  `isTokenError` (`err.isTokenError === true`), цикл приостанавливается с сообщением пользователю
  о необходимости пополнить баланс и ввести `retry`.

### Ограничения
- Инструменты работают только с абсолютными путями и заранее известными директориями
  (`BASE_DIR`, `BILLS_LEDGER_DOCX_PATH`, шаблонная папка "Сордису"); произвольные пути вне этих
  директорий инструментами не создаются и не читаются, кроме явно переданных `filePath`/`monthDir`.
- Все входные данные валидируются схемой Zod (`tool.schema`) внутри `callTool` — вызов с
  несоответствующими типами/значениями enum отклоняется (ZodError) до входа в обработчик.
- Классификация категорий (`electricity`/`heat`/`water`/`garbage`/`maintenance`) — фиксированный
  enum, никаких произвольных категорий инструменты не принимают.

## 1. `download_bills_from_yandex`
(`src/tools/download-bills.tool.ts`)

| | |
|---|---|
| **Когда** | В начале ReAct-цикла `bills`, шаг 1 (`runBillsReactCycle`), перед анализом документов. Сейчас в `runBillsReactCycle` скачивание выполняется напрямую через `YandexDiskService`, а не через этот инструмент — инструмент существует как альтернативный путь вызова. |
| **Аргументы** | `docsDir?: string` — опциональный путь к папке docs; по умолчанию `./docs` относительно `process.cwd()`. |
| **Обработка результата** | `DownloadBillsResult: { success, docsDir, fileCount, filePaths, fileNames }` — источник истины о том, что и куда скачано. |
| **Обработка ошибок** | Исключения `syncDocsToLocal` распространяются к вызывающему коду. Сетевые ошибки скачивания с диска retry-ятся внутри `YandexDiskService` (до 3 раз, задержка 2s→4s→8s), сам инструмент retry не делает. |
| **Ограничения** | Перед скачиванием папка `docsDir` очищается от предыдущего содержимого — инструмент нельзя использовать для инкрементального докачивания без потери старых файлов. |

## 2. `organize_bills`
(`src/tools/organize-bills.tool.ts`)

| | |
|---|---|
| **Когда** | Шаг 4 `runBillsReactCycle`, сразу после успешной валидации всех 5 категорий (`validation.valid && validation.details.length > 0`). Вызывается напрямую агентом, не через LLM tool-calling. |
| **Аргументы** | `bills: { filePath: string; category: enum }[]` — строится агентом напрямую из `validation.details` (только записи с `category !== null`), а не через парсинг ответа модели, чтобы исключить потери данных. |
| **Обработка результата** | `OrganizeBillsResult: { monthName, monthDir, placedCount, placedFiles }`; агент логирует сводку, дальше использует `monthDir` в последующих шагах (дозапись таблицы, генерация счёта "Сордису"). |
| **Обработка ошибок** | Ошибка организации файлов логируется (`console.error`), но **не прерывает** цикл — `validation` возвращается как есть, потому что сама валидация уже прошла успешно. |
| **Ограничения** | Для категорий `electricity`/`heat` создаётся дополнительная промежуточная папка `1292`. Рядом с файлами сохраняется служебный манифест `_expected_amount.json` со списком реально перенесённых файлов счетов — используется позже, чтобы отличить счета от прочих документов при проверке квитанций; манифест обязательно удаляется в шаге 7 после завершения цикла. |

## 3. `check_bill_receipts`
(`src/tools/check-receipts.tool.ts`)

| | |
|---|---|
| **Когда** | По команде пользователя `continue`/`continue!` (`BillsCycleService.checkBillReceipts`), после того как пользователь оплатил счета и положил квитанции в те же папки. |
| **Аргументы** | `monthDir?: string` — если не передан, используется папка текущего месяца по умолчанию. |
| **Обработка результата** | Прямой вызов: агент получает `ReceiptsCheckResult`. `ok=false` → цикл приостанавливается, пользователю показываются проблемные папки (`getFailedReceiptFolders`). |
| **Обработка ошибок** | Любая ошибка сервиса — исключение, прерывающее выполнение вызывающего кода (в отличие от "мягких" шагов ReAct-цикла). |
| **Ограничения** | Сравниваются только факты наличия квитанции, суммы не сопоставляются. Классификация каждого файла-кандидата всегда идёт через HARD-режим (RouterAI), локальная модель не используется — решение принимается роутером до вызова инструмента, само решение и модель логируются в консоль. При `continue!` неподтверждённые категории передаются дальше как `excludeCategories` в `generate_sordisu_bill`, а не приводят к остановке. |

## 4. `generate_sordisu_bill`
(`src/tools/generate-sordisu-bill.tool.ts`)

| | |
|---|---|
| **Когда** | Последний шаг цикла `continue`/`continue!`, только если по всем папкам (или по всем, кроме принудительно исключённых через `continue!`) подтверждены квитанции. |
| **Аргументы** | `excludeCategories?: enum[]` — список категорий без подтверждённой квитанции, собранный агентом через `getFailedReceiptCategoryKeys(result)`; передаётся только при `continue!`. |
| **Обработка результата** | Прямой вызов: агент получает `GenerateSordisuBillResult` (пути к PDF, суммы, предупреждения, `excludedCategories`) и формирует финальное сообщение пользователю; после этого CLI завершает процесс (шаг 8). |
| **Обработка ошибок** | Ошибка на любом из под-шагов (заполнение счёта/справки/коммуналки, копирование документов) — исключение, прерывающее финализацию цикла. |
| **Ограничения** | Категории, исключённые из-за отсутствия квитанции, не включаются в расчёт итоговой суммы справки-расчёта и не копируются в папку счёта "Сордису". Суммы по категориям берутся строго из данных, извлечённых моделью через `extractBillColumns` (HARD-режим) — инструмент сам не парсит счета. |
