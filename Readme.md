# Возможности
Этот агент предназначен для работы со счетами (ReAct-цикл валидации коммунальных счетов) или простым общением с локальной моделью gemma4:e4b-8k используя провайдер Ollama.
При выборе мода работы со счетами (`bills`) документы автоматически скачиваются из Яндекс.Диска в папку `docs` проекта (YandexDiskService: GET-запрос на получение ссылки для скачивания по PUBLIC_URL_DOCS из .env с заголовком Authorization: OAuth <YANDEX_OAUTH из .env>, скачивание архива, разархивация и перенос файлов в docs). Указание пути к папке или файлу не требуется.

## Краткое описание инструментов

Инструменты агента — именованные функции с описанием и Zod-схемой аргументов, вызываемые
напрямую внутри процесса через типизированный диспетчер `callTool` (`src/tools/registry.ts`).
MCP-сервер и протокол не используются: внешних потребителей инструментов нет, а единственный
клиент (сам агент) работает в том же процессе.

| Инструмент | Назначение |
|---|---|
| `download_bills_from_yandex` | Скачивает документы счетов с Яндекс.Диска в папку `docs` (альтернативный путь вызова для LLM tool-calling; в реальном цикле `bills` скачивание сейчас идёт напрямую через `YandexDiskService`). |
| `organize_bills` | Раскладывает провалидированные счета по папкам месяца/категории (электричество, тепло, вода, мусор, содержание помещения), вызывается напрямую агентом по результатам валидации, без обращения к модели. |
| `check_bill_receipts` | Проверяет по команде `continue`/`continue!` фактическое наличие квитанции в каждой папке категории (только факт наличия, без сравнения сумм); классификация каждого файла — через RouterAI (HARD-режим). |
| `generate_sordisu_bill` | Формирует итоговые документы "Сордису" (счёт, справка-расчёт, счёт-коммуналка) на основе данных, извлечённых моделью из счетов; поддерживает исключение категорий без подтверждённой квитанции (`continue!`). |

## Метрики успеха команды `bills`

- **Покрытие категорий** — доля из 5 обязательных категорий (электричество, тепло, вода, мусор,
  содержание помещения), подтверждённых документами за цикл без ручных исправлений
  (`coveredCategories.length / 5`, поле результата `runBillsReactCycle`).
- **Успешность валидации за одну попытку** — доля запусков `bills`, дошедших до
  `validation.valid === true` без необходимости в `retry` (нехватка документов/токенов).
- **Точность распознавания квитанций** — доля папок, в которых `check_bill_receipts` верно
  определил наличие/отсутствие чека без ложных срабатываний, из общего числа папок за цикл
  (метрика по `getFailedReceiptFolders`).
- **Доля циклов без принудительного `continue!`** — чем выше, тем реже пользователю приходится
  продолжать цикл с неподтверждёнными категориями (исключёнными из финальных документов).
- **Время цикла до финальных документов "Сордису"** — от старта `bills` до успешного
  `generate_sordisu_bill`, включая паузы на оплату (Human-in-the-Loop), но не включая их в чистое
  время обработки.
- **Устойчивость к сбоям** — доля циклов, не прерванных сетевыми ошибками скачивания
  (после 3 автоматических retry) или исчерпанием токенов RouterAI (`isTokenError`).

## Оценка качества агента (evals) и защита

Подсистема evals (`src/evals/`) измеряет три метрики успешного ответа модели на gold set:

| Метрика | Как считается |
|---|---|
| **Успех** | Детерминированная сверка ответа с эталоном (без LLM-as-judge): обязательные факты `mustContainAny`, маркеры честного отказа `refusal`, запрещённые маркеры `mustNotContain`, анти-галлюцинация `mustNotFabricate`. Проверки — `src/evals/metrics.ts`. |
| **Время** | Полная латентность ответа (векторный поиск + генерация), мс; в отчёте avg/p95/max, у кейса опциональная граница `maxLatencyMs`. |
| **Стоимость** | Руб. за ответ: для ask/askMeters (локальная Ollama) — 0; для документных задач (RouterAI) — по `usage` ответа и тарифам `ROUTERAI_INPUT_RUB_PER_1M`/`ROUTERAI_OUTPUT_RUB_PER_1M` из .env (накопление — `RouterAIService`, сводка за сессию печатается при выходе из CLI). |

Gold set — `src/evals/gold-set.json`: эталонные вопросы к таблице учёта (ask) и показаниям
счётчиков (askMeters) на реальных данных, плюс негативные кейсы (честный отказ при отсутствии
данных, устойчивость к prompt-injection).

Запуск: `npm run evals` (требуются запущенные Ollama и FalkorDB, актуализированная векторная
база). Отчёт печатается в консоль и сохраняется в `data/evals/report.json`; код выхода 1,
если есть проваленные кейсы. Фильтр: `npx tsx src/evals/run-evals.ts --case <id>`.

Базовые механизмы защиты агента:
- **Prompt-injection**: системные промпты ask/askMeters запрещают выполнять инструкции из
  вопроса пользователя; gold-кейсы типа `injection` регрессионно проверяют устойчивость.
- **Галлюцинации**: промпты требуют отвечать только по контексту; refusal-кейсы проверяют,
  что при отсутствии данных модель честно отказывается, а не выдумывает суммы/даты.
- **Санитизация вывода**: `sanitizeModelOutput` (src/llm/ollama-helper.ts) срезает
  markdown-конструкции, ломающие разметку Telegram-клиента.
- **Лимит генерации**: `num_predict` ограничен `OLLAMA_MAX_RESPONSE_TOKENS` (по умолчанию 2048).

# Как работает ReAct-цикл (порядок вызова инструментов)

Цикл реализован по паттерну Reasoning → Act: **Reasoning** выполняет модель (структурированный
JSON-ответ — валидация или классификация документа), а **Action** — детерминированный оркестратор
`BillsCycleService` (`src/services/BillsCycleService.ts`), который по результату ответа модели
вызывает инструменты напрямую внутри процесса. Модель **не выбирает** инструменты сама:
последовательность шагов задана в коде, LLM применяется только там, где нужно понять содержимое
документа (валидация категорий, классификация квитанций, извлечение столбцов). Цикл управляется
человеком (Human-in-the-Loop): `bills`/`retry` — итерации валидации, `continue`/`continue!` —
вторая фаза после оплаты.

## Конечный автомат состояний цикла

За состояние отвечает поле `billsCyclePhase` в `BillsCycleService`:

| Состояние            | Значение                                                       | Переходы |
|----------------------|----------------------------------------------------------------|----------|
| `idle`               | Цикла нет (или он завершён).                                    | `bills` → `running` |
| `running`            | Идёт валидация / ждёт добавления документов или пополнения баланса. | успешная валидация → `awaitingPayment`; `retry` → повтор той же итерации |
| `awaitingPayment`    | Цикл приостановлен на оплату, ждёт `continue` / `continue!`.     | успешная `continue`/`continue!` (генерируются документы) → `idle` |

- Фатальное исключение внутри итерации оставляет цикл в `running`, чтобы `retry` был доступен.
- Команда `retry` в `idle` (когда цикла нет) отвергается с ошибкой; `continue` вне
  `awaitingPayment` — тоже.

## Итерация 1 (команды `bills` / `retry`): валидация и раскладывание

Одна итерация — метод `runBillsValidationStep` → `runBillsReactCycle`. Шаги выполняются
строго в указанном порядке:

| Шаг | Действие | Чем выполняется | Поведение при ошибке |
|-----|----------|-----------------|----------------------|
| 1 | Скачать документы с Яндекс.Диска в папку `docs` | `YandexDiskService.syncDocsToLocal` (прямой вызов сервиса, **не tool**) | Ошибка → `valid=false`, вернуть отчёт; цикл ждёт `retry` (внешний слой YandexDiskService делает до 3 авто-retry со схемой 2s→4s→8s) |
| 2 | Собрать пути файлов (`./docs`, расширения `.xlsx/.xls/.pdf/.doc/.docx/.odt`) | `DocumentsService.resolveBillFilePaths` | Ошибка → `valid=false`, отчёт, ждём `retry` |
| 3 | Валидация категорий счетов (5 обязательных: electricity/heat/water/garbage/maintenance) | `agentModelRouter.validateBillCategories` → роутер логирует решение (для `bills` всегда HARD), выгружает классификатор из Ollama (`keep_alive=0`) и вызывает RouterAI с промптом `BILLS_VALIDATE_SYSTEM_PROMPT`; при сетевой ошибке RouterAI — fallback на локальную Ollama по извлечённому тексту | 401/402 (`isTokenError`) → проброс без fallback, цикл приостанавливается до `retry`; остальные ошибки → `valid=false` с описанием |
| 4 | Разложить файлы по папкам месяца/категорий | **tool `organize_bills`** через `callTool`; аргументы `{bills: [{filePath, category}]}` строятся **напрямую из `validation.details`** (без парсинга LLM), проходят Zod-валидацию; создаёт `<Месяц>/` и папки категорий (для electricity/heat — промежуточная `1292/`), копирует файлы, пишет манифест `_expected_amount.json` в каждую папку | Ошибка только логируется, цикл не прерывается |
| 5 | Дозаписать строку в таблицу учёта (суммы по категориям из `validation.details`) | `DocxBillsTableService.appendMonthlyRow` | Ошибка логируется, цикл не прерывается |
| 6 | Актуализировать векторную базу FalkorDB для режима `ask` | `BillsLedgerVectorService.syncLedgerToVectorStore` | Ошибка логируется, цикл не прерывается |
| 7 | Удалить служебные манифесты `_expected_amount.json` из `docs` | `deleteExpectedAmountManifests` (helper из `organize-bills.tool.ts`) | Ошибка логируется |

Результат итерации:
- `validation.valid === true` → цикл переходит в `awaitingPayment`, печатается отчёт и приглашение
  оплатить счета и набрать `continue`.
- Нет документов / не покрыты все 5 категорий / `isTokenError` / фатальная ошибка → цикл остаётся
  в `running`, программа ждёт команду `retry`.

## Итерация 2 (команды `continue` / `continue!`): проверка квитанций и финальные документы

`continueBillsCycle(force)` выполняет два tool-вызова последовательно:

| Порядок | Tool | Что делает | Используемая модель |
|---------|------|------------|---------------------|
| 1 | **`check_bill_receipts`** | `ReceiptVerificationService.checkAllFolders`: находит все папки с манифестом `_expected_amount.json`; кандидаты = файлы, кроме исходных счетов и манифеста; каждый кандидат классифицируется через `agentModelRouter.verifyReceiptFile` (квитанция/чек или посторонний документ — УПД, акт, договор). Посторонние игнорируются, папка успешна при хотя бы одной квитанции; суммы не сравниваются | RouterAI (HARD, режим кэширован по команде `bills`); при сетевой ошибке — fallback на локальную Ollama |
| 2 | **`generate_sordisu_bill`** | Выполняется, если все папки успешны **или** передано `continue!` (тогда провалившиеся категории исключаются). Внутренний порядок вызовов: `createMonthFolderFromTemplate` → `fillAndConvertBillDoc` (счёт .doc→pdf) → `fillAndConvertSpravkaDoc` (справка-расчёт: табличные данные счетов извлекаются через `agentModelRouter.extractBillColumns` — RouterAI с fallback на Ollama) → `fillAndConvertKommunalkaDoc` (счёт-коммуналка по итогам справки) → `copyOrganizedDocsToMonthFolder` (копирует разложенные счета/квитанции в папку месяца «Сордису») | extractBillColumns: RouterAI (HARD), fallback — Ollama |

Итог:
- `receipts.ok === false` и не force → возвращается `receiptsFailed`, печатается отчёт с папками
  и причинами; цикл **остаётся** в `awaitingPayment` — пользователь докладывает квитанции и снова
  печатает `continue`, либо `continue!` для принудительного продолжения без этих категорий.
- Успех → цикл генерирует документы, переводится в `idle` и завершается (CLI печатает итоги,
  Telegram-клиент завершает дочерний процесс).

## Механика вызова инструментов

- Все инструменты описаны контрактом `AgentTool` (`src/tools/types.ts`): `name`, `title`,
  `description`, Zod-`schema` аргументов, `execute(args)`.
- Единая точка входа — `callTool` (`src/tools/registry.ts`): диспетчер с перегруженными
  типизированными сигнатурами. Аргументы валидируются Zod-схемой до входа в обработчик
  (несоответствие → ZodError), тип результата выводится из имени инструмента.
- MCP/внешний протокол не используется: вызов — обычный вызов функции внутри процесса агента.
- Tool `download_bills_from_yandex` зарегистрирован для LLM tool-calling как альтернативный путь,
  но основной цикл скачивает документы прямым вызовом `YandexDiskService` (шаг 1).
- Каждый шаг логируется в консоль с префиксом `[ReAct]` / `[Роутер]` (файл, режим, выбранная
  модель, ошибки), поэтому по логу восстанавливается точная последовательность вызовов.

Правила поведения каждого инструмента (когда вызывается, обработка результата/ошибок,
ограничения) — см. `src/tools/tools-sop.md`.

# Telegram-клиент
Альтернативный интерфейс к агенту через Telegram-бота (`--telegram`). Бот работает как отдельный процесс-наблюдатель: по команде `/start` он порождает дочерний процесс `npm run --silent start` (CLI-режим) и транслирует его stdout в чат, а текстовые сообщения из чата передаёт в stdin агента. Поэтому все моды (`ask`, `meters`, `askMeters`, `report`, `bills`, `retry`, `continue`, `continue!`) доступны в Telegram точно так же, как в терминале.

## Настройка
В `.env` добавьте:
```
TELEGRAM_BOT_TOKEN=<токен от BotFather>
TELEGRAM_ALLOWED_CHAT_IDS=<chatId через запятую, например 123456789,987654321>
```
Если `TELEGRAM_ALLOWED_CHAT_IDS` пуст — бот открыт для всех (в консоль выводится предупреждение).

## Запуск
```
npm run start:telegram
```

## Команды бота
- `/start` — запустить агента (или подключиться к уже запущенному)
- `/stop` — остановить агента (SIGINT дочернему процессу)
- `/status` — проверить, запущен ли агент
- любой текст — передаётся агенту как команда CLI (например `ask сколько была оплата за теплоэнергию в августе 2026`)

## Особенности
- Вывод агента собирается построчно, отфильтровываются баннеры npm/nodemon, длинные сообщения разбиваются на части до 4000 символов с разрывом по строкам.
- Каждый чат имеет собственный дочерний процесс агента.
- При завершении агента (команда `exit` или завершение цикла `bills`) бот остаётся работать и сообщает о завершении; можно снова нажать `/start`.
- При завершении агента (`exit`, Ctrl+C/SIGINT, закрытие терминала) выполняется выгрузка всех загруженных моделей Ollama из памяти (`ChatProcessor.cleanup` → `OllamaHelper.unloadAllModels`, аналог цикла `ollama ps` + `ollama stop <модель>`), чтобы локальная модель не оставалась работающей в фоне. Если агент завершился аварийно и модели остались в памяти, их можно выгрузить вручную командой `npm run model:down` (`src/scripts/unload-models.ts`).

# Моды
1. ask - режим вопрос-ответ по содержимому таблицы учёта коммунальных платежей ("Администрирование_2_0.docx"), хранящейся в векторной базе FalkorDB (команда `ask <вопрос>`, например `ask сколько была оплата за теплоэнергию в августе 2026`)
2. meters - ввод показаний счётчиков электроэнергии и водоканала (команда `meters el-00000,vod-00000`, например `meters el-02345,vod-00317`)
3. askMeters - вопрос-ответ по таблицам показания счётчиков, аналогично режиму ask (команда `askMeters <вопрос>`, например `askMeters какое показание счётчика электроэнергии было в июле 2026 года`)
4. bills - ReAct-цикл валидации коммунальных счетов с Human-in-the-Loop
- Агент скачивает документы с Яндекс.Диска (PDF, DOC/DOCX, XLS/XLSX, ODT) и передает их в RouterAI (промпт BILLS_VALIDATE_SYSTEM_PROMPT)
- Модель анализирует документы и проверяет покрытие 5 категорий: электричество, тепло, вода, мусор, содержание помещения
- Счета на оплату И счета-фактуры (УПД, УКД) являются валидными документами
- При нехватке документов — вывод недостающих категорий и ожидание команды `retry`
- При исчерпании токенов RouterAI — цикл приостанавливается с уведомлением, после пополнения баланса — `retry`
- При сетевых ошибках скачивания — автоматический retry до 3 раз с задержкой 2s→4s→8s
- При успешной валидации счета автоматически раскладываются по папкам месяца/категорий (organize_bills) — раскладывание выполняется напрямую по данным валидации, без обращения к модели
- После раскладывания цикл приостанавливается и предлагает оплатить счета; после оплаты пользователь вводит `continue`
- По `continue` вызывается tool `check_bill_receipts`, который проверяет только фактическое наличие квитанции (чека) в каждой папке — сравнение сумм не выполняется
- Для каждого файла-кандидата в папке (кроме самих счетов) классификация всегда выполняется через RouterAI, без обращения к локальной модели (подробнее — раздел "Роутинг моделей" ниже). Файл/модель всегда логируется в консоль. Чек/квитанция считается найденной, посторонние документы (УПД, акты, договоры) игнорируются и не считаются ошибкой
- Если в какой-то папке квитанция не найдена — цикл снова приостанавливается с подсветкой ошибки (с указанием конкретной папки) и ожиданием `continue`
- Если ввести `continue!` (с восклицательным знаком) вместо `continue` — цикл принудительно продолжится дальше, даже если в одной или нескольких папках квитанция не найдена; итоговые счета "Сордису" (счёт, справка-расчёт, счёт-коммуналка) будут сформированы без указания категорий/ресурсов, по которым не найден чек, а сами документы этих категорий не попадут в папку счетов "Сордису"

# Роутинг моделей (единый роутер EASY/HARD)
Выбор модели для ЛЮБОЙ задачи агента проходит через единый роутер — `ModelRouter`
(`src/llm/routing/model-router.ts`, экспортируется как `agentModelRouter`). Больше нет двух
отдельных независимых схем: сначала всегда вызывается роутер, и только по его решению
выполняется обращение к конкретной модели.

- **EASY → локальная модель Ollama.** Реализация обращения — `OllamaHelper`
  (`src/llm/ollama-helper.ts`), создаётся напрямую в `ChatProcessor`
  (`src/llm/chat-processor.ts`). Модель задаётся `OLLAMA_MODEL` (по умолчанию `gemma4:e4b-8k`).
- **HARD → облачная модель RouterAI.** Реализация обращения — `RouterAIService`
  (`src/services/RouterAIService.ts`; модель задаётся `AIROUTER_MODEL`, например
  `google/gemini-3.5-flash`, ключ — `AIROUTER_API_KEY`).

## Как роутер принимает решение

Свободного текстового чата в агенте нет: общение с моделью доступно только через команды,
неизвестный ввод игнорируется (Telegram-клиент в будущем будет просто зеркалить ту же логику).
Поэтому решение о режиме принимает **локальная модель-классификатор** (`OLLAMA_ROUTER_MODEL`,
по умолчанию та же `OLLAMA_MODEL`) по **описанию возможностей команды** — статической таблицы
режимов больше нет. Для каждой команды в `src/llm/prompts.ts` задано описание
(`AGENT_TASK_DESCRIPTIONS`), и классификатор по промпту `ROUTER_SYSTEM_PROMPT` отвечает словом
EASY или HARD:

- **HARD** — задача связана с чтением/распознаванием документов (файлы, сканы, PDF, счета,
  квитанции, таблицы) → выполняет RouterAI.
- **EASY** — любая другая задача (ответ по векторному контексту, запись чисел, генерация отчёта
  по готовым данным) → выполняет локальная Ollama.

Ожидаемые решения классификатора:

| Команда            | Режим | Модель | Обоснование в описании команды |
|--------------------|-------|--------|--------------------------------|
| `bills`            | HARD  | RouterAI | в описании явно указаны распознавание и валидация документов, проверка квитанций |
| `meters`           | EASY  | локальная Ollama (фактически не вызывается) | ручной ввод чисел и запись в таблицу, без чтения документов |
| `ask`, `askMeters` | EASY  | локальная Ollama | ответ по уже проиндексированному векторному контексту |
| `report`           | EASY  | локальная Ollama (фактически не вызывается) | генерация .docx по уже проиндексированным данным |

Решение классификатора детерминировано описанием команды, поэтому **кэшируется по команде в пределах
сессии**: повторные операции той же команды (например, проверка каждой квитанции в цикле `bills`)
не дёргают классификатор заново. После выбора маршрута локальная модель-классификатор выгружается
из памяти Ollama (`keep_alive=0`), чтобы не греть CPU на фоне, пока задачу выполняет RouterAI.

Если классификатор недоступен (ошибка Ollama), режим не выбирается молча — ошибка пробрасывается
наверх, поскольку без локальной модели роутинг невозможен.

## Fallback RouterAI → Ollama

Документные операции (HARD) выполняет RouterAI, но при его **недоступности** (сетевая ошибка,
5xx, таймаут) роутер автоматически переключается на локальную Ollama: из документа извлекается
текст (`pdftotext`, для `.doc`/`.docx` — через конвертацию LibreOffice во временный PDF) и
передаётся локальной модели с тем же системным промптом. Это резервный, более слабый по качеству
путь (локальная модель не видит визуальную разметку документа).

Fallback **не** выполняется при ошибках конфигурации RouterAI: 401 (невалидный ключ) и 402
(кончился баланс, `isTokenError`) — эти ошибки пробрасываются как есть, и цикл `bills` при 402
приостанавливается до `retry`. Если недоступны обе модели (RouterAI и Ollama) — ошибка выводится
пользователю.

## Через роутер выполняются

- `agentModelRouter.validateBillCategories` — анализ документов и определение категорий счетов
  (шаг валидации ReAct-цикла `bills`), вызывается из `BillsCycleService.runBillsReactCycle`.
- `agentModelRouter.verifyReceiptFile` — классификация каждого файла-кандидата в папке при
  `check_bill_receipts` (квитанция/чек или иной документ), вызывается из
  `ReceiptVerificationService.classifyCandidate`.
- `agentModelRouter.extractBillColumns` — извлечение табличных данных счёта (единица, количество,
  сумма, НДС) при генерации счёта "Сордису"/справки-расчёта, вызывается из
  `SordisuBillGeneratorService.aggregateCategoryColumns`.

Вызывающий код (BillsCycleService, ReceiptVerificationService, SordisuBillGeneratorService) больше не
обращается к `RouterAIService` напрямую — только через `agentModelRouter`, который сам определяет
режим и делегирует вызов (с fallback на локальную модель при недоступности RouterAI, см. выше).
Принятое решение и выбранная модель всегда логируются в консоль
(например `[Роутер] Проверка квитанции — <файл>: режим HARD. Модель для задачи — RouterAI (<модель>)`).
При исчерпании токенов/баланса RouterAI выполнение прерывается с `isTokenError`, и цикл `bills`
приостанавливается до `retry`.

# Векторный поиск по таблице учёта (ask)
- Данные из таблицы учёта коммунальных платежей хранятся в векторной базе FalkorDB (узел :BillRow, эмбеддинги через Ollama nomic-embed-text).
- Актуализация происходит автоматически в реакт-цикле bills после дозаполнения docx-таблицы (переиндексация с нуля: удаление старых узлов/индекса и создание нового на основе всех строк таблицы).
- Команда `ask <вопрос>` в CLI выполняет векторный поиск по FalkorDB, формирует контекст из найденных строк и передаёт его вместе с вопросом в модель (Ollama), которая отвечает только на основе этого контекста.
- Перед использованием `ask` векторная база должна быть актуализирована хотя бы один раз (через `bills`), иначе будет возвращена ошибка о пустом индексе.
- FalkorDB поднимается локально через Docker (`npm run db:up`, docker-compose.yml), настройки — в .env (FALKORDB_HOST/PORT/GRAPH, OLLAMA_EMBED_MODEL).
- Режим `talk` удалён: вся бизнес-логика свободного чата заменена на `ask` (ответы только по таблице учёта).

# Показания счётчиков (meters / askMeters)
- Данные из таблиц "электроэнергия.docx" и "водоканал.docx" (папка "Показания счетчика") хранятся в векторной базе FalkorDB (узел каждой строки — `:MeterRow`, отдельно от `:BillRow`).
- Команда `meters el-00000,vod-00000` (количество цифр может быть любым) добавляет в каждую из двух таблиц новую строку (текущая дата в формате ДД.ММ.ГГ + числовое показание из el/vod соответственно), затем переиндексирует векторную базу по обновлённым таблицам целиком.
- При некорректном вводе (не соответствует формату "el-цифры,vod-цифры") выводится ошибка, таблицы и векторная база не изменяются.
- Команда `askMeters <вопрос>` работает по аналогии с `ask`: векторный поиск по `:MeterRow` и ответ модели только на основе найденного контекста.
- Пути к docx-таблицам настраиваются в .env: `METERS_ELECTRICITY_DOCX_PATH`, `METERS_WATER_DOCX_PATH`.

# Отчёт по периоду (report)
- Команда `report MM/YY-MM/YY` (например `report 05/26-08/26`) формирует отдельный .docx-отчёт с таблицей сумм по услугам за указанный диапазон месяцев (включительно).
- Формат таблицы отчёта совпадает с таблицей учёта "Администрирование_2_0.docx": месяц | теплоэнергия | электроэнергия | содержание помещения | водоканал | вывоз мусора.
- Данные берутся напрямую из актуальной таблицы учёта (файл не изменяется, только читается).
- Отчёт сохраняется в папку `/home/geekonclick/Рабочий стол/Администрирование2026` (переопределяется переменной `BILLS_REPORT_OUTPUT_DIR` в .env) с именем вида `Отчёт_05.2026-08.2026.docx`.
